## 二、带依赖关系的执行顺序

```
[阶段 0 · Day 1，可并行]
  P0-4 (密钥/口令强约束)  ── 零依赖、零新依赖、半天搞定 ──┐
  P0-1 (持久化真PG 或 诚实单实例) ── 上线前提，独立 ───────┤
  P0-3 (注入防护+金额硬阈值) ── 小改、独立 ───────────────┘
        │
        ▼
[阶段 1 · Day 2-3]
  P0-2 (重试退避+幂等)  ── 依赖先拍板"真实工具接口形态" ── 若本期仍模拟，至少落地幂等骨架+退避钩子
        │
        ▼
[阶段 2 · P1 工程化，按依赖推进]
  P1-2 (trace_id 全链路日志)  ← 地基，必须先做
        │
        ├─► P1-7 (lint/mypy)  ┐
        ├─► P1-6 (测试增强)    ├─ 为 CI 准备
        ├─► P1-8 (依赖锁)     ┘
        │
        ▼
  P1-1 (CI 流水线)  ← 收口：跑上面三项 + pip-audit
        │
        ▼
  P1-3 (Prometheus 指标+告警)  ← 推荐依赖 P1-2 关联 trace
        │
        ▼
  P1-4 (模型治理+评测) → P1-5 (异常分类) → P1-9 (审批超时) → P1-10 (recursion_limit)
        │
        ▼
[阶段 3 · P2 演进]  全部后置，下一迭代
```

**为什么这个顺序最优：**
1. **先把 4 个 P0 按"零依赖低成本 → 上线前提 → 小改 → 依赖决策"排序**：P0-4 改动最小、不引入新依赖、立刻消除"被接管"风险，放第一刀；P0-1（数据不丢）是其余上线动作的前提，与 P0-4 并行；P0-3 小改即可堵审批绕过；P0-2 因依赖"真实工具接口"决策，放最后拍板，但本期至少留幂等骨架。
2. **P1 内先打地基再收口**：`P1-2 trace_id` 是全链路日志、指标归因、故障复盘（D5）的共同前置，必须先做；`P1-6/7/8` 是 CI 要跑的对象，先就位再上 `P1-1 CI` 才不会"空跑流水线"；`P1-3 指标` 依赖 trace 才能做请求级关联。这样避免"先搭 CI 没东西可跑"或"先上指标无法串联"的返工。
3. **P2 全部后置**：均不阻塞"能否安全上线"，是成本/体验/合规优化，放在 MVP 上线后的迭代，避免本轮范围蔓延。

## 三、我建议你先做哪 1 条，为什么

**建议先做 P0-4（生产密钥/口令强约束）。**

理由：
- **它是 4 个 P0 里唯一"零依赖、零新增依赖、改动最小、可逆、影响面最窄"的**，半天内可完成并独立上线，不触碰核心编排与持久化。
- **事故后果直接且不可逆**：默认 `admin/admin123` + 弱 `SECRET_KEY`，意味着任何能访问服务地址的人都能登管理员、导出全部审计与用户；弱密钥还能被伪造 JWT。这是"被接管 + 合规穿透"级别的事故，而 P0-1（数据丢失）在单实例挂载卷下尚可接受、P0-2/P0-3 需"接真 LLM/真 API"才暴露。
- **不依赖任何其他项**，可以先于持久化/注入/幂等单独合入，立刻降低暴露面；即便其余 P0 还在排期，先堵这个口子也是净收益。

> 次优先是 **P0-1**：如果你们计划多副本/高可用，必须真接 PG；若本期明确单实例，则可采"诚实标注单实例 + `replicas: 1`"的最小方案，把"真接 PG"降级为按需项。
