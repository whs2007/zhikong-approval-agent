# 「智控」企业级智能工作流平台 — 审计与安全设计

> 文档版本：v1.0
> 前置文档：《01-需求分析说明书》《03-数据库与持久化设计》
> 编制日期：2026-10-29

> 说明：用户明确要求"开发过程中要有审计"。本平台把**审计**同时作为（A）系统功能能力 与（B）研发过程合规活动，二者在本设计中统一呈现。

---

## 第一部分：系统审计子系统（功能性审计）

### 1. 审计目标
- **可追溯**：任意一个工作流实例（thread_id）可还原"谁、在何时、做了什么、结果如何"。
- **不可篡改**：审计记录 append-only，无修改/删除接口。
- **可合规**：满足企业审批留痕、AI 决策溯源、操作问责要求。
- **可导出**：支持监管抽查的 CSV/JSON 导出。

### 2. 审计数据模型
见《03-数据库与持久化设计》§3 `audit_log` 表。关键字段：`trace_id`、`thread_id`、`event_type`、`actor`、`actor_role`、`node`、`phase_before`、`phase_after`、`detail`、`level`、`created_at`。

### 3. 审计切入点（在代码中埋点）
`AuditService.append(...)` 在以下位置调用：
1. 工作流提交前后（WORKFLOW_SUBMIT）
2. 每个节点进入/退出（NODE_ENTER/NODE_EXIT，含耗时）
3. 风险分析完成（RISK_ANALYZED，含命中规则与 LLM 用量）
4. 进入人工审批（APPROVAL_PAUSED）
5. 审批决策（APPROVAL_DECISION，含操作人、意见、通过/驳回）
6. 执行开始/结果（EXEC_START/EXEC_RESULT）
7. 每次重试（RETRY，含失败原因与第几次）
8. 流程结束（WORKFLOW_DONE）
9. 登录成败（AUTH_LOGIN/AUTH_FAIL）
10. 知识库重载（KNOWLEDGE_RELOAD）

### 4. 审计查询与导出
- `GET /audit/logs`：多条件组合过滤（thread_id/actor/event_type/时间区间/分页）。
- `GET /audit/trace/{trace_id}`：按追踪号还原完整链路。
- `GET /audit/export?format=csv|json`：只读导出，供合规归档。

### 5. 审计与业务解耦
- 审计写入失败**不影响**主流程（降级为告警日志），保证业务可用性同时不丢关键事件。
- 审计库与 Checkpointer、业务库物理可分离（生产建议独立库/实例）。

## 第二部分：安全设计

### 6. 认证（Authentication）
- JWT（HS256），`python-jose` 签发；有效期默认 60 分钟，可配。
- 登录：`POST /auth/login` 校验 `username` + bcrypt 哈希密码。
- 密码存储：bcrypt 哈希，明文不落库。

### 7. 授权（Authorization / RBAC）
- 角色：`applicant` / `approver` / `admin`。
- 依赖注入 `Depends(require_roles([...]))` 在路由层校验。
- 关键约束：
  - 审批接口仅 `approver`/`admin`。
  - 审计查询/导出仅 `admin`。
  - 提交接口 `applicant`/`admin`。

### 8. 传输与数据保护
- 生产建议 TLS（反向代理/Nginx 终止）。
- 审计 `detail` 中敏感字段（如金额）按需脱敏展示；密码永不出现在日志/审计。

### 9. 接口安全
- 统一异常处理器，避免堆栈泄露。
- 参数经 Pydantic 强校验，防注入。
- 频率限制（进阶）：登录接口加基础限流。

## 第三部分：研发过程审计（Process Audit）

> 这是"开发过程中要有审计"的直接落地：在每个开发阶段设置审计检查点，由审计员（可为本项目评审角色）出具审计记录，确保交付可控、可验收。

### 10. 过程审计检查点

| 阶段 | 检查点 | 审计产出 | 通过标准 |
|------|--------|----------|----------|
| 需求 | 需求评审 | 《需求评审记录》 | 需求覆盖 FR-01~FR-08，验收标准明确 |
| 设计 | 设计评审 | 《设计评审记录》 | 架构/数据/接口/审计设计一致、可落地 |
| 编码 | 代码评审 | 《代码评审记录》 | 分层清晰、无硬编码密钥、审计埋点完整 |
| 测试 | 测试评审 | 《测试评审记录》 + pytest 报告 | 核心用例全绿、覆盖率达标 |
| 交付 | 交付评审 | 《交付审计报告》 | 文档+代码+部署物齐备，可运行 |

### 11. 过程审计记录模板
```
审计项：<阶段检查点>
审计日期：YYYY-MM-DD
审计依据：对应技术文档版本
审计发现：<符合项 / 不符合项 / 风险>
审计结论：通过 / 有条件通过 / 不通过
整改跟踪：<若不符合，责任人+时限>
```

### 12. 本项目的审计执行
本项目在交付阶段将附带：
- 《过程审计报告》（含上述各检查点结论）
- `tests/` 下自动化用例与运行结果
- 代码埋点对照表（审计事件 ↔ 代码位置）

## 第四部分：合规映射

| 合规诉求 | 平台对应能力 |
|----------|--------------|
| 操作问责 | audit_log.actor + 角色 + 时间戳 |
| AI 决策可解释 | RISK_ANALYZED 记录命中规则与上下文 |
| 流程不可抵赖 | append-only 审计 + JWT 操作人绑定 |
| 数据留存 | 审计保留策略（§《03》7） |
| 最小权限 | RBAC 角色约束 |
