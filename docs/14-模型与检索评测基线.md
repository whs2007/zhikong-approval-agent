# 14. 模型与检索评测基线（P1-5）

> 目标：把"质量"从**主观声明**变成**可回归的数字**。评审报告中"0 评测"一项由此关闭。

## 1. 设计取向：为什么不用 RAGAS

同类项目（如 `Anshu1-ux/enterprise-document-agent`）用 RAGAS 评测 RAG 质量。本项目**不采用**，原因：

| 方案 | 依赖 | 能否进 CI | 结论 |
|---|---|---|---|
| RAGAS（用 LLM 评 LLM） | 需要真实 LLM API Key + 网络 | 否（CI 无密钥、结果不稳定、有成本） | 只能做离线抽样报告 |
| 本项目：确定性评测 | 零依赖（规则模型 + 离线向量检索） | 是（每次提交都跑） | **采用** |

本项目的默认链路本身就是**确定性的**（规则风险分级 + 本地 n-gram 检索），没有随机性，
因此评测也应当是确定性的——这样它才能成为 CI 的一道门禁，而不是一份"只在汇报时用"的 PDF。

## 2. 评测集构成

文件：`zhikong/evals/cases.jsonl`（19 条，JSONL 便于 diff 与增补）

| 类别 | 条数 | 判分标准 | 为什么这样判 |
|---|---|---|---|
| `risk` | 6 | `risk_level` 与期望**完全一致** | 金额阈值分级是硬业务规则，错一级就会导致漏审批 |
| `injection` | 3 | 风险等级**不得低于**期望下限 | 注入只可能试图"降级"，故判下限而非等值 |
| `retrieval` | 10 | 上下文必须含关键片段；其中 2 条要求**top-1 命中**；1 条为**负例**（无关查询不得召回） | 只判"是否召回"会被 `top_k` 调大刷满分；负例防止"总有召回"的自欺 |

## 3. 当前基线

```
risk       6/6     (100%)
injection  3/3     (100%)
retrieval  10/10   (100%)
总计：19/19   准确率 100.0%   阈值 90%
```

运行：`cd zhikong && python scripts/run_eval.py`（`--json` 输出机器可读，`--threshold` 自定义阈值）

## 4. 本轮评测暴露并修复的真实缺陷

评测**不是**一次就 100%——最初的 15 条用例确实 100%，但那是假通过。补入判别性用例后掉到 **84.2%**，
暴露出三个真实问题，随后修复：

| 缺陷 | 现象 | 修复 |
|---|---|---|
| **排序不准** | "紧急采购的预算上限" 召回正确但 top-1 是错误条款（第二条被第一条压过） | 引入**混合检索**：向量余弦 + 词项覆盖率加权融合（`HYBRID_LEXICAL_WEIGHT`，默认 0.5） |
| **无关查询也硬凑上下文**（幻觉温床） | "今天食堂菜单有什么" 仍召回含 `CFO` 的采购条款 | 增加最小相关度阈值（`RELEVANCE_MIN_SCORE`，默认 0.12），低于阈值不返回 |
| **门槛失效**（自查发现） | 首版把"归一化后的融合分"当门槛，而归一化是相对本次查询做的 → top-1 恒为 1.0，门槛形同虚设 | 门槛改用**绝对量纲**（词项覆盖率），排序才用相对分 |

> 这条经验值得记住：**评测先要能失败，才有价值**。一个第一次跑就满分的评测集，通常只说明它太弱。

## 5. 如何扩展

1. 在 `evals/cases.jsonl` 追加一行（字段见文件首行注释与 `scripts/run_eval.py` 的判分逻辑）；
2. 跑 `python scripts/run_eval.py` 确认基线未回退；
3. 若新增用例失败且确认是**系统缺陷**（非期望写错），修复后更新本文件的"当前基线"。

后续可增补的方向（P2）：
- 接入真实 LLM 时的**一致性**评测（同一输入多次采样的一致率）；
- 审批人链路由正确性（`required_approvers` 与制度条款逐条比对）；
- 端到端耗时基线（P95）。
