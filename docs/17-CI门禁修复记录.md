# CI 门禁修复记录（首次推送后）

> 记录时间：2026-10-30
> 触发场景：仓库首次推送到 GitHub，CI 第一次在**真实 GitHub Runner**上运行
> 结果：`质量门禁` 与 `安全门禁` 两个 job 均红，但**代码本身没问题**——红的是门禁自身。

---

## 一、现象

首次 push 后 CI 运行 51s，两个 job 失败：

| Job | 失败步骤 | 同 job 内其他步骤 |
|---|---|---|
| 质量门禁（ruff / mypy / pytest） | ❌ 依赖锁一致性 | ✅ ruff / mypy / pytest / 离线评测 全过 |
| 安全门禁（依赖漏洞 / 秘密扫描） | ❌ 秘密扫描（gitleaks） | ✅ pip-audit（No known vulnerabilities found） |

关键观察：**被门禁保护的代码全部通过，只有门禁自己失败**。这类红最容易误判为"代码坏了"。

---

## 二、根因（两个，都是门禁设计缺陷）

### 2.1 依赖锁一致性：把"锁定"误做成"追最新"

原实现 `gen_lock.py --check` 会重新执行：

```python
pip install --dry-run --ignore-installed --report ... -r requirements.txt
```

拿到**当前 PyPI 上最新的完整依赖树**，再与 `requirements.lock.txt` 逐行比对。

CI 报出的差异：

```
锁文件已过期，请运行 make lock：
  langchain-core==1.7.1
  langsmith==0.14.15
  opentelemetry-api==1.45.1
  pydantic==2.14.1
  pydantic_core==2.50.1
```

这 5 个包在锁里、不在新解析结果里——即**上游这两天发布了新的 langgraph 依赖树**，锁文件本身完全正确。

**语义错误**：依赖锁的语义是「锁定一组**已知可用**的版本」，不是「永远等于 PyPI 最新版」。用后者做校验，等于让 CI 随时间必然变红（哪怕一行代码没改）。

### 2.2 gitleaks：首次推送时 auto 生成的 revision range 非法

`gitleaks/gitleaks-action@v2` 会自动拼出：

```
--log-opts=cf73e689d29b32f7a95c57d6c2b4813409badd19^..1b18a622c3d926d7c82575991fddf1bfd4230918
```

`cf73e68` 是**根提交，没有父节点**，`cf73e68^` 不存在 → `git log` 报错 → action 判定 `stderr is not empty` → exit 1。

而同一份日志里明确写着：

```
ERR failed to scan Git repository error="stderr is not empty"
WRN no leaks found in partial scan
```

**没有发现泄露**，只是扫描命令本身跑挂了。这是"首次 push"独有的边界情况，日常增量推送不会触发。

---

## 三、修复

### 3.1 `gen_lock.py --check` 改为离线静态校验

不再联网重解析，只回答两个**可确定**的问题：

1. `requirements.txt` 的每个直接依赖，锁里是否有精确版本？
2. 锁里的版本是否满足 `requirements.txt` 的约束（含上界）？

传递依赖的完整性由「生成时固化」保证，运行时由 pip 安装失败暴露。

`--check` 现在**完全离线、确定性、秒级**，且不会随上游发版而漂移。

### 3.2 gitleaks 改为直接跑官方二进制

```yaml
- name: 秘密扫描（gitleaks，全历史）
  working-directory: .
  run: |
    curl -sSfL -o /tmp/gitleaks.tar.gz ".../gitleaks_8.24.3_linux_x64.tar.gz"
    tar -xzf /tmp/gitleaks.tar.gz -C /tmp gitleaks
    /tmp/gitleaks git --config "${GITHUB_WORKSPACE}/.gitleaks.toml" \
      --redact --no-banner --verbose --exit-code 2 \
      --log-opts="--all" "${GITHUB_WORKSPACE}"
```

显式 `--log-opts=--all`，不再依赖 action 推断的 revision range；扫描**全部历史**（能满足"已删除但曾出现过"的检测需求）。

新增 `.gitleaks.toml`：只做 allowlist（演示口令 / 监控演示令牌 / mock 占位 key / tests 与 docs 路径），**不关闭任何规则类别**。

## 四、证据

### 4.1 锁校验：正例 + 4 个负例

```
$ python scripts/gen_lock.py --check
锁文件一致：57 个包，直接依赖全部覆盖且版本满足约束        EXIT=0

# 缺少直接依赖
锁文件与 requirements.txt 不一致：
  - 依赖 httpx 在 requirements.txt 中声明，但锁文件缺少精确版本   EXIT=1

# 版本违反约束
  - fastapi==0.100.0 不满足 requirements.txt 约束 >=0.110        EXIT=1

# 上界约束
  - pydantic==3.1.0 不满足 requirements.txt 约束 >=2.5,<3.0      EXIT=1

# 锁文件格式非法
  - 锁文件含 1 行非法格式（应为 name==version）：garbage line    EXIT=1
```

已固化为 `tests/test_gen_lock.py`（9 例），纳入常规 `pytest`。

### 4.2 gitleaks：正例 + 负例（用 v8.24.3 官方镜像实跑）

```
# 正例：本项目全历史
$ gitleaks git --config .gitleaks.toml --log-opts=--all .
INF 13 commits scanned.
INF no leaks found                                    EXIT=0

# 负例：临时仓库注入一个真实格式的 GitHub PAT（ghp_ + 36 位）
$ gitleaks git --log-opts=--all /repo
WRN leaks found: 1                                    EXIT=2
```

**一个从不报错的门禁等于没有门禁**，所以负例是必须的。

> 插曲：第一次负例用的是 `AKIAIOSFODNN7EXAMPLE`（AWS 官方文档示例值），gitleaks **故意**不报——它是公开示例密钥。换成随机生成的真实格式 token 才触发。这说明默认规则是"精确"而非"宽松"的。

## 五、教训（可复用到其他项目）

1. **门禁的红/绿要能区分「代码问题」与「门禁问题」**。本次两个红都在"代码全过、只有检查器自身失败"，如果直接改代码去迎合门禁，会引入真正的坏改动。
2. **依赖锁的校验必须是确定性、离线的**。任何"重新向 registry 求解"的校验都会随时间漂移，最终被人加 `continue-on-error` 关掉——那才是真正的安全损失。
3. **首次推送是 CI 的边界态**。根提交没有父节点、默认分支刚创建、action 推断 range 失败，这些只在第一次出现，容易被"本地全绿"掩盖。
4. **安全扫描必须有负例**。只验证"没报错"证明不了它有能力报错。

## 六、遗留（诚实标注）

- gitleaks 只扫描**当前仓库历史**，不覆盖 GitHub 上的 PR 评论、Issue、Actions 日志中的临时输出。这些需组织级 secret scanning（GitHub Advanced Security）兜底。
- `.gitleaks.toml` 对 `tests/` 与 `docs/` 是**整目录放行**。若将来有人把真实凭据写进测试或文档，本门禁不会拦。这是刻意的取舍（否则假凭据噪声会淹没真问题），代价由 code review 承担。
- 依赖锁只锁 `requirements.txt`，**未锁 `requirements-dev.txt`**（ruff/mypy/pip-audit 版本仍浮动）。生产镜像不受影响，但 CI 工具版本可能漂移。
