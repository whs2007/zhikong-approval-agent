> 文档版本：v1.0
> 前置文档：《01-需求分析说明书》《02-系统架构设计》

## 1. 数据分层

平台涉及三类"存储"，职责分离：

| 存储 | 用途 | 实现 | 是否业务可改 |
|------|------|------|--------------|
| **Checkpointer** | LangGraph 工作流状态快照、断点、恢复 | `SqliteSaver`/`PostgresSaver` 内部表（`checkpoints`/`writes` 等） | 否（框架管理） |
| **审计库** | 全链路操作审计（append-only） | 自建 `audit_log` 表（SQLAlchemy） | 否（仅追加） |
| **业务库** | 用户、知识库元数据、统计等 | 自建 `users` 等表 | 是 |

默认统一落盘到 SQLite 文件（`data/db/zhikong.db`），生产可切 PostgreSQL（改连接串即可）。

---

## 2. Checkpointer（工作流状态持久化）

由 LangGraph 框架自动管理，核心表（以 SQLite 为例）：

- `checkpoints`：每个 `(thread_id, checkpoint_ns, checkpoint_id)` 对应一次状态快照。
- `checkpoint_writes`：节点写入的 pending 数据（用于 `interrupt` 恢复）。
- `checkpoint_blobs`：大对象（状态值）存储。

**设计要点**：
- `thread_id` 为工作流实例唯一标识，跨天/重启恢复的唯一钥匙（FR-03-3）。
- 状态快照天然支持"图级别循环重试"的回放（FR-04-2）。
- 业务不直连这些表，统一经 `WorkflowService` 的 `get_state`/`update_state` 访问。

## 3. 审计库（Audit Store）

### 3.1 `audit_log`（核心审计表，append-only）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK AUTOINCREMENT | 自增主键 |
| `trace_id` | VARCHAR(64) | 全局追踪号（一次提交贯穿全程） |
| `thread_id` | VARCHAR(64) | 关联工作流实例 |
| `event_type` | VARCHAR(32) | 事件类型（见 3.2） |
| `actor` | VARCHAR(64) | 操作主体（用户ID/角色/system） |
| `actor_role` | VARCHAR(32) | 操作人角色 |
| `node` | VARCHAR(32) | 关联节点（analyst/approval/...） |
| `phase_before` | VARCHAR(32) | 状态变更前 |
| `phase_after` | VARCHAR(32) | 状态变更后 |
| `detail` | TEXT | 事件详情（JSON，如审批意见/LLM 摘要） |
| `level` | VARCHAR(16) | INFO/WARN/ERROR |
| `created_at` | DATETIME | 事件时间（UTC+8 存储） |

**索引**：`(thread_id)`、`(created_at)`、`(event_type)`、`(actor)`。

**不可篡改性**：仅提供 `INSERT`（经 `AuditService.append`），不提供 UPDATE/DELETE 接口；导出为只读。

### 3.2 审计事件类型（EventType）

| 事件 | 触发点 | 关键 detail |
|------|--------|-------------|
| `WORKFLOW_SUBMIT` | 提交申请 | request 摘要、风险预估值 |
| `NODE_ENTER` / `NODE_EXIT` | 节点进入/退出 | 节点名、耗时 |
| `RISK_ANALYZED` | 分析完成 | 风险等级、命中规则、LLM 用量 |
| `APPROVAL_PAUSED` | 进入人工审批 | 风险等级、金额 |
| `APPROVAL_DECISION` | 审批人决策 | 通过/驳回、意见、审批人 |
| `EXEC_START` / `EXEC_RESULT` | 执行开始/结果 | 成功/失败、重试次数 |
| `RETRY` | 重试发生 | 第几次、失败原因 |
| `WORKFLOW_DONE` | 流程结束 | 最终状态 |
| `AUTH_LOGIN` / `AUTH_FAIL` | 登录成败 | 用户、失败原因 |
| `KNOWLEDGE_RELOAD` | 知识库重载 | 文档数 |

## 4. 业务库

### 4.1 `users`（用户与角色）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | VARCHAR(36) PK | UUID |
| `username` | VARCHAR(64) UNIQUE | 登录名 |
| `hashed_password` | VARCHAR(128) | bcrypt 哈希 |
| `role` | VARCHAR(16) | applicant/approver/admin |
| `display_name` | VARCHAR(64) | 显示名 |
| `created_at` | DATETIME | 创建时间 |
| `is_active` | BOOLEAN | 是否启用 |

### 4.2 `knowledge_docs`（知识库元数据，可选）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | VARCHAR(36) PK | UUID |
| `source` | VARCHAR(255) | 文档来源路径 |
| `title` | VARCHAR(255) | 标题 |
| `chunk_count` | INT | 分块数 |
| `updated_at` | DATETIME | 更新时间 |

> 向量本身存于 `VectorStore`（默认 Numpy/FAISS 内存或本地索引文件），元数据登记于此便于管理。

## 5. 实体关系（ER 简化）

```
users(1) ──< (提交/审批) ── workflow(thread_id, Checkpointer 管理)
users(1) ──< audit_log(actor) >── workflow(thread_id)
knowledge_docs(1) ──< 向量块(VectorStore)
```

- 一个用户可发起多个工作流、做出多次审批决策。
- 审计记录通过 `actor` 关联用户、`thread_id` 关联工作流，形成完整溯源链。

---

## 6. 持久化与恢复流程（跨天审批）

```
Day1 18:00  提交 → analyst 完成 → 命中 interrupt_before → Checkpointer 落盘(thread_id=X)
Day1 23:00  服务重启 → Checkpointer 文件仍在
Day2 09:30  审批人提交决策 → 用 thread_id=X 的 config 调用 update_state → invoke(None) 恢复
           → executor 执行 → monitor → END
全程 audit_log 追加记录，thread_id=X 可查完整链路
```

---

## 7. 数据保留与归档（建议）

- 审计日志：保留 ≥ 180 天，超期按 `created_at` 归档到历史表/冷存储。
- Checkpointer：已完成（END）线程的快照可定期清理以控体积。
- 业务库：用户/知识库长期保留。

## 8. 迁移与初始化

- 使用 SQLAlchemy `create_all`（MVP）或 Alembic（生产）建表。
- 首次启动自动创建默认管理员账号（`admin`/`admin123`，强制首次改密建议）。
- 知识库目录 `data/knowledge/` 放置 `*.txt/*.md`，启动时加载；提供重载接口。
