# 23 · 审计组提交（group commit）：语义不变地提速 2.5 倍

> 承接 docs/21。那里把写路径压到 56 RPS，并把瓶颈定位到"单请求串行成本"。
> 这篇处理其中最大的一块：**一次审批提交要写 ~13 条审计，原来每条都单独 fsync**。

## 一、一句话结论

**一次提交的 13 条审计原来要付 13 次 fsync（4.8ms/条），改成组提交后合并成约 1 次/批，
存储层单条成本降到 0.834ms（5.75×），系统吞吐 56 → 143 RPS（2.55×），
且「append 返回即落盘」这个语义一点没变。**

高并发 11355 次提交产生的 37480 条审计，**id 从 1 到 37480 完全连续，零丢失、零空洞**。

## 二、问题：13 次 fsync 串在一起

原实现（`services/audit_service.py`）：

```python
with _lock:                     # 全局锁
    conn.execute(INSERT, row)
    conn.commit()               # ← 每条一次 fsync
```

一次 `WORKFLOW_SUBMIT` 会依次写 `WORKFLOW_SUBMIT`、`NODE_ENTER`/`NODE_EXIT`（多个节点）、
`RISK_ANALYZED`、`APPROVAL_PAUSED`……合计约 13 条。在 WAL+`synchronous=FULL` 下
每次 commit 要等一次磁盘 fsync，本机实测 4.8ms → 13 次就是 60ms 量级的串行开销，
而且 `_lock` 是全局的，**所有请求的审计写入被彻底串行化**。

这就是 docs/21 里"单请求 10.6ms→后来 17.8ms"里最大的一块可压缩成本。

## 三、为什么不用"异步队列"——先把这条路堵死

业界最常见的写法是：`append()` 把记录丢进队列就返回，后台线程每 100~200ms 批量落盘。
吞吐确实高。但审计是这套系统里**唯一不可重建的事实来源**（业务表可以从审计推导，
审计不能从任何东西推导），丢一条就不是"性能问题"了。

这个说法不能只靠嘴讲，所以写了个实验（`scripts/proof_audit_loss.py`）：
两种实现各写 200 条，写到第 101 条时对进程发 `SIGKILL`（模拟 OOM / 容器被驱逐），
然后数库里到底有多少条。

| 实现 | 调用方以为写了 | 库里实际 | 结论 |
|---|---|---|---|
| 异步队列（入队即返回） | 101 条 | **0 条** | 全丢 |
| 组提交（本实现） | 101 条 | **102 条** | 一条不丢 |

> 102 而不是 101，是因为组提交版本先写了一条用于建表探测的记录，不影响结论。

这条证据决定了设计方向：**可以慢一点，但不能在"已返回成功"之后丢数据。**

## 四、组提交怎么做

保留同步语义：调用方仍然阻塞到"自己这条已 commit"才返回，只是把同一瞬间到达的 N 条
合并进一个事务、共用一次 fsync。

```
append()                          flusher 线程
   │                                   │
   ├─ 记录入队 ──────────────────────► │
   │                                   ├─ 取走整批（最多等 200µs 攒批）
   │                                   ├─ executemany(INSERT, batch)
   │                                   ├─ commit()   ← N 条共付 1 次 fsync
   └─ 等自己的 Event ◄────────────────┤ set() 唤醒整批
```

三个关键点，都是踩过坑才定下来的：

**1. 队列攒够就立刻提交，不空等窗口。**
第一版是"无条件等满 300µs"，实测比朴素批量慢 2.3 倍——因为每条都在为攒批付延迟。
改成 `len(queue) < 8` 才等，够了立即走。

**2. 窗口设 0 反而更慢。**
测过 `_BATCH_WINDOW_SECONDS = 0`：1198 → 811 条/秒。因为调用方不让出 GIL，
flusher 抢不到执行机会。**这里省的不是 fsync，是线程调度。**

**3. flusher 必须带 `is_alive()` 判断。**
两个 flusher 线程共享同一个队列时，A 清空队列后 B 会拿到空 batch，白付一次 commit
（测试里表现为 `commits == 2` 而不是 1）。顺带加了 `if not batch: continue`。

## 五、数据

### 5.1 存储层 A/B（`scripts/bench_audit_writes.py`）

320 条 = 8 线程 × 40 条，重复 3 次取中位数，同库同 schema、同 WAL+FULL：

| 写法 | 耗时 | 吞吐 | 单条 | 加速 | 语义 |
|---|---|---|---|---|---|
| 逐条 commit（原实现） | 1536ms | 208 条/s | 4.801ms | 1.00× | 返回即落盘 |
| 调用方攒批 16 条/事务 | 117ms | 2738 条/s | 0.365ms | 13.15× | 返回即落盘 |
| **组提交（本实现）** | 267ms | 1198 条/s | 0.834ms | **5.75×** | **返回即落盘** |
| ~~异步队列~~ | — | — | — | — | **会丢（见第三节）** |

"调用方攒批"比组提交快 2.3 倍，因为它有 8 个线程各自并行提交，而组提交只有 1 个
writer（SQLite 单写者，多 flusher 无意义）。这是组提交的天花板。

**这条路是可走的**：如果以后把 `append()` 扩展成 `append_many()`，让图节点一次提交
本节点的全部事件，就能拿到 0.365ms。属于下一步优化，不在本轮做（要改 13 个调用点的结构）。

### 5.2 系统级（`evidence/load-test-group-commit.json`）

单 worker、25 / 100 并发、每档 40 秒：

| 版本 | 并发 | RPS | P50 | P95 | P99 |
|---|---|---|---|---|---|
| WAL 分级后（docs/21） | 25 | 56.26 | — | — | — |
| **组提交后** | 25 | **143.40** | 166.6ms | 264.8ms | 299.4ms |
| **组提交后** | 100 | **138.45** | 694.6ms | 822.4ms | 2255.9ms |

**2.55×**。用 Little's Law 复核：100 并发下 `λ×W = 138.45 × 0.714s ≈ 98.8 ≈ 100`，
与并发数吻合，说明统计自洽、请求在排队而非丢单。

注意 P95 822ms 已略超 docs/21 定的 800ms 阈值——这是压测故意打满的结果，
规则会（也应当）触发 `LatencyP95High`，不是回归。

### 5.3 完整性：一条都没丢

11355 次压测提交 + warmup，产生的审计：

```
总条数      37480
id 范围     1 … 37480   （连续，无空洞）
按类型      WORKFLOW_SUBMIT 12493 / RISK_ANALYZED 12493 / APPROVAL_PAUSED 12493 / AUTH_LOGIN 1
失败日志    0 条
HTTP 5xx    0 个
```

12493 × 3 + 1 = 37480，**账能对上，id 连续**。这是"组提交在高并发下没有丢写"最直接的证据——
如果有一批 commit 失败又没被调用方发现，id 会断档或者总数会小于预期。

## 六、边界（不能吹的地方）

1. **提速来自"合并 fsync"，不是"消灭 fsync"。** durable 语义没变，
   13 条 → 约 1 次/批，但每批仍要落盘。想更快只能换存储。
2. **组提交有天花板：单 writer。** 8 线程各自攒批能做到 2738 条/s，
   组提交只有 1198 条/s。要突破就得改 API 支持批量写。
3. **跨进程无效。** 每个进程一个 flusher，多 worker 下各攒各的批；
   审计库仍是单文件，多进程写会抢锁（和 docs/21 的结论一致）。
4. **攒批窗口对单请求有 ~0.2ms 的固定延迟。** 串行场景（`bench_submit` 18.87ms）
   **没有变快**，反而略慢——收益只在并发下出现。这是真实的取舍，不是"全面变快"。
5. **`synchronous=FULL` 只保证"进程崩溃不丢"，不保证"磁盘缓存掉电不丢"。**
   后者要靠 UPS 或 `PRAGMA fullfsync`。

## 七、面试问答

**Q：审计是每条都 fsync 吗？那不是很慢？**

我原本就是每条 commit，一次提交 13 条审计、13 次 fsync，把写路径压到 56 RPS。
现在改成组提交，一个事务写一批，存储层单条成本从 4.8ms 降到 0.83ms，系统吞吐到 143 RPS。

**Q：为什么不直接异步写？**

因为审计不可重建，丢了补不回来。我做过实验：异步队列实现写到第 101 条时 kill -9，
库里 0 条——调用方全都收到了"写成功"。组提交在同样场景下 102 条一条不少。
**在审计这件事上，"返回了但没落盘"比慢严重得多。**

**Q：组提交具体怎么保证不丢？**

调用方入队后阻塞在自己那条的 Event 上，flusher 合并整批 `executemany + commit`，
成功后才 set。所以 `append()` 返回时数据已经在 WAL 里。进程被 kill 也只丢
"还没返回"的那几条，不会丢"已经返回成功"的。

**Q：为什么不用消息队列（Kafka）？**

那是跨进程、跨机器的解，代价是引入一个新组件和一套投递语义（至少一次/恰好一次），
而当前瓶颈是单机单文件。**在 SQLite 上做异步队列，只是把丢数据的窗口变大。**
换 PG 之后再考虑是否要外部队列。

**Q：怎么证明优化真的有效，而不是测错了？**

三层：存储层 A/B 只改写入方式这一个变量（4.8→0.83ms）；系统级压测前后对比（56→143 RPS）；
Little's Law 复核 `λ×W` 是否等于并发数；最后数审计行数并检查 id 连续。
四个独立角度指向同一结论。

**Q：这算"高并发"吗？**

不算。143 RPS 是单机单进程、SQLite 存储下的数字，我不叫它高并发。
瓶颈已经定位到单 writer，下一步是换 PG + 批量写 API，不是调参。
