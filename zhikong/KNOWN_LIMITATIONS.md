# 已知边界（KNOWN LIMITATIONS）

> 这份文件只回答一个问题：**这个项目做不到什么。**
>
> 目的不是自曝其短，而是让每一处"没做"都有明确的原因、影响和替代方案。
> 面试被问到时，能直接指出边界并解释判断，比含糊其辞安全得多。
> 每一条都标注了代码位置，随时可以打开给人看。

## 一句话版（先背这段）

> 这是个**单机、SQLite 存储、离线模型**的完整业务闭环，强在流程与工程约束，
> 不强在容量与智能。写路径实测 25–97 RPS（取决于磁盘 fsync），瓶颈是每次请求
> 3 次事务提交 + SQLite 单写锁，加 worker 无效；按"可重建性"做 WAL 分级后到 56 RPS。
> 向量索引不落盘；PG 只覆盖 Checkpointer；评测是 19 题固定集，不是准确率。

## A. 存储与持久化

| # | 边界 | 代码位置 | 影响 | 被问到怎么答 |
|---|---|---|---|---|
| A1 | **FAISS 索引不落盘**。`index_path` 参数收了但从未 `write_index/read_index` | `workflows/providers.py` `FaissVectorStore.__init__` | 每次启动全量重算 embedding；多副本各建一份 | "单机内存索引，13 个知识块没必要落盘。要做得加 write_index + meta 校验（embedder_id/维度），否则换了 embedding 模型会静默用错索引。" |
| A2 | **仍是 SQLite 单文件**。已统一 WAL 并按"能否重建"分级 durable，但写仍串行 | `core/sqlite_utils.py` | 单写者，跨进程抢文件锁，多 worker 扩容无效（docs/21 实测）；`NORMAL` 下断电可能丢最后几个 checkpoint | "压测证明加 worker 无效；WAL 分级把单进程吞吐从 25 提到 56 RPS，但只有换 PG 才能水平扩展。" |
| A5 | **checkpoint 无归档/清理**：实测 1.5 万次提交后 `cp.db` 91MB、`writes` 表 15 万行 | `workflows/graph.py` | 长期运行磁盘持续增长；大表下的检索退化未验证 | "没做 TTL。生产要按 thread 完成时间归档或分区，否则库只涨不降。" |
| A3 | **无 schema 迁移**，三处手写 `CREATE TABLE IF NOT EXISTS` | `services/audit_service.py`、`idempotency_service.py`、`models/user.py` | 加字段只能手工 ALTER，无版本、无回滚 | "演示项目没引 Alembic。生产第一个 PR 就补，否则上线改表全靠人肉。" |
| A4 | **PG 只覆盖 Checkpointer**，auth/audit 仍 SQLite | `workflows/graph.py` `CHECKPOINTER=postgres` 分支 | 多副本时工作流状态能共享，但用户与审计仍各写各的 | "我验证的是'Checkpointer 可切'，不是'全栈 PG'。代码注释里也写了：水平扩展前必须一起迁。" |

## B. 容量与并发

| # | 边界 | 依据 | 影响 | 被问到怎么答 |
|---|---|---|---|---|
| B1 | **写路径上限 25–97 RPS**（单进程，取决于磁盘 fsync） | docs/21 §4.4：同代码快盘 94、慢盘 25、WAL 分级后 56 | 审批提交低频，够用；但不能对外说"高并发" | 给数字必须带磁盘条件，别只报最大值 |
| B2 | **加 worker 无效**：4 worker 仍 95 RPS，P95 1.1s→2.3s | docs/21 §4.3 | 扩容必须先换存储，否则只是加剧锁竞争 | "试过，数据在这。所以优化顺序是先 PG 再加副本。" |
| B3 | **压测不在 CI 里** | `.github/workflows/ci.yml` 只有质量/安全门禁 | 性能回归无法自动发现 | "压测要起服务跑 4 分钟，放 CI 成本高；现在是发版前人工跑，结果入库。" |

## C. 可靠性

| # | 边界 | 代码位置 | 影响 | 被问到怎么答 |
|---|---|---|---|---|
| C1 | **没有图级重试**，重试下沉在工具层 | `workflows/tools.py`（`retryable` 分类 + 退避） | 节点内工具失败会重试；节点整体失败不会重跑整图 | "刻意下沉：重跑整图会重复写审计、重复调 LLM，副作用不可控。工具层重试更精确。" |
| C2 | **SSE 不支持断线续传**。发了 `id: {seq}`，但服务端不读 `Last-Event-ID` | `services/workflow_service.py` `_sse()` | 网络抖动后前端拿不到补发事件，只能重新查 `/status` | "事件没做缓冲，重连靠 `GET /status/{thread_id}` 兜底；要做续传得有环形缓冲 + 游标。" |
| C3 | **线程池未显式配置** | `workflow_service` 用 `asyncio.to_thread`；SSE 由 `StreamingResponse` 迭代同步生成器 | 并发超过池大小后排队（docs/21 首字节 532ms） | "默认池（to_thread 是 min(32, CPU+4)，anyio 是 40），没调过。首字节劣化就是池排队的证据。" |

## D. 可观测

| # | 边界 | 影响 | 被问到怎么答 |
|---|---|---|---|
| D1 | 三条告警规则中，`LLMDegradation` 与 `LatencyP95High` 做过真实触发演练；`ErrorRateHigh` 仅验证表达式可算 | 5xx 路径没有可靠的人工注入手段，未演练送达 | "错误率规则只验证了计算；另外两条有截图和送达记录（docs/22）。" |
| D2 | 有 `trace_id` 贯穿 HTTP→日志→审计，但**没接 Jaeger/Tempo** | 跨服务追踪做不了，只能同进程按 id grep | "trace id 是自己串的，够单机排查；接 OTel 是下一步。" |
| D3 | 没有 SLO 看板与错误预算 | 告警阈值是静态的，不随业务量调整 | "阈值按压测数据定（800ms），不是按错误预算算的。" |
| D4 | 抓取曾因线程池被业务占满而超时（`up=0`），已改为后台刷 Gauge | 若未来把 CPU 而非线程池打满，抓取仍可能变慢 | "压测时告警不响，查到 `/metrics` 和业务抢线程池；改后台刷新后抓取稳定在 3ms。" |

## E. 安全

| # | 边界 | 影响 | 被问到怎么答 |
|---|---|---|---|
| E1 | **无限流、无登录防爆破**（全库无 `rate_limit`） | 可被暴力破解或打满 | "JWT + RBAC 有了，限流没做。生产要在网关或中间件加，且登录失败要计数锁定。" |
| E2 | 演示用 `METRICS_TOKEN` 明文写在 compose / prometheus.yml | 令牌可被仓库读者拿到 | "已标注为演示令牌，生产走 secret 注入并定期轮转。" |
| E3 | 审计是 append-only（代码不提供改删 API），但**无防篡改**（无 hash 链） | 有数据库写权限的人可直接改记录 | "append-only 是应用层约束，不是密码学保证。要防篡改得加 prev_hash 链。" |

## F. 智能能力

| # | 边界 | 影响 | 被问到怎么答 |
|---|---|---|---|
| F1 | 默认 embedding 是**离线 n-gram**，不是语义向量 | 同义改写召回弱，只能靠词项兜底 | "默认离线是为了零依赖可跑；切 Sentence-Transformers 只需改一个配置，但会引入模型下载。" |
| F2 | 评测是 **19 条固定用例**，不是准确率 | 不能对外说"准确率 94%" | "19/19 通过，样本太小，只能证明回归没坏，不能证明泛化。" |
| F3 | 拒答阈值是**启发式**（词项覆盖率绝对值） | 换语料/换语言要重调 | "用的是绝对覆盖率而非相对分数，因为相对分数在只有 1 条命中时也会很高，会误答。" |

## 刻意不做（及原因）

这几项不是"没来得及"，是判断后不做——面试时说清楚比硬做好：

| 项 | 为什么不做 |
|---|---|
| Kubernetes | 瓶颈是单文件存储，不是编排；上 K8s 只会把瓶颈复制到更多 Pod |
| 微服务拆分 | 当前是单体且调用链短，拆开要引入分布式事务与跨服务追踪，收益为负 |
| 消息队列 | 审批是低频同步操作，没有削峰填谷的需求；引入后要处理重复消费与顺序 |
| 多租户 | 需求里没有；加 tenant_id 会污染所有查询与审计 |
| 前端框架重构 | 页面只有一个看板，原生 SPA 够用；重构的收益是"更好维护"，不是"更能讲" |
